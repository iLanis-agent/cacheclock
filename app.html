CacheClock

Paste response headers. See if a cache may store the response, how long it stays fresh, and what its age is right now.
Rules follow RFC 9111. Storing (section 3): no-store blocks; private blocks a shared cache; Authorization blocks a shared cache unless public, must-revalidate or s-maxage is present; something must allow storing (public, max-age, Expires, s-maxage for shared, a private directive for a private cache, or a status that is heuristically cacheable: 200, 203, 204, 206, 300, 301, 308, 404, 405, 410, 414, 501). Freshness lifetime (4.2.1): s-maxage for shared caches, else max-age, else Expires minus Date, else a heuristic: 10% of the time since Last-Modified, which the RFC calls typical and does not require. Age (4.2.3): apparent age is response time minus Date (never below 0), corrected age is the Age header plus the request-to-response delay, the larger one is the initial age, and the current age adds the time stored. A response is fresh while lifetime is greater than age. no-cache means a stored copy is reused only after revalidation; must-revalidate forbids serving it stale. Invalid max-age values and invalid Expires dates are treated as stale. If a directive appears twice this page uses the first and says so. Real browsers and CDNs add their own rules (for example the Vary header, request directives, stale-while-revalidate, immutable), which this page does not model. 308 in the heuristic status list comes from RFC 9110 and I could not read that section as text. Runs in your browser, nothing stored.
